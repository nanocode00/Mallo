# Talkiosk 설문 결과 반영에 따른 파이프라인 변경안

> **문서 상태:** 임시 분석  
> **기준:** 고령 사용자 키오스크 이용 경험 및 음성 주문 인터뷰, 현재 응답 13명  
> **작성일:** 2026-08-19  
>
> 본 문서는 현재까지 수집된 설문 결과를 바탕으로 기존 Talkiosk 파이프라인의 변경 필요성을 정리한 문서이다.  
> 설문 응답은 추가될 수 있으므로, 아래 내용은 최종 요구사항 확정안이 아니라 **MVP 기능 우선순위와 설계 방향을 조정하기 위한 탐색적 분석**으로 사용한다.

---

## 1. 결론 요약

설문 결과를 반영하더라도 Talkiosk의 기존 파이프라인을 전면 변경할 필요는 없다.

기존의 핵심 구조인

```text
Mic
 → STT
 → Menu Candidate Matching
 → Rule-based NLU
 → Schema Validator
 → Order Engine
 → TTS / GUI
```

는 그대로 유지할 수 있다.

다만 기존의 **음성 주문 명령 중심 구조**에서 다음 기능을 추가하는 방향으로 확장할 필요가 있다.

- 메뉴 탐색 및 추천
- 메뉴 정보 질문
- 주문 수량·옵션 수정
- 직전 동작 취소 및 복구
- 현재 주문 내용 확인
- 다시 설명
- 천천히 설명
- 화면과 음성을 함께 이용한 주문 확인

즉, 프로젝트의 방향이 바뀌었다기보다 기존 구조에서 **어떤 기능을 더 중요하게 다뤄야 하는지 설문을 통해 구체화된 것**에 가깝다.

## 2. 설문에서 확인된 주요 신호

### 2.1 현재 표본 특성

| 항목 | 현재 결과 | 해석 |
|---|---:|---|
| 응답자 수 | 13명 | 소규모 탐색 표본 |
| 연령 | 60~64세 6명 / 65~69세 7명 | 70대 이상 응답자 없음 |
| 최근 키오스크 이용 | 1개월 이내 11명 | 최근 사용 경험 기반 |
| 스마트폰 숙련 | 앱 설치·온라인 결제 이상 8명 | 비교적 디지털 숙련도가 높은 편 |
| 동행 여부 | 대부분/항상 동행 9명 | 혼자 사용하는 상황의 표본이 부족 |

따라서 현재 결과는 전체 고령 사용자에게 일반화하기보다 **비교적 활동적이고 디지털 기기 사용 경험이 있는 60대 사용자**의 초기 경향으로 해석하는 것이 적절하다.

향후에는 다음 집단을 추가로 확보할 필요가 있다.

- 70대 이상 사용자
- 전화·문자 위주로 스마트폰을 사용하는 사용자
- 혼자 키오스크를 사용하는 사용자
- 키오스크 사용 빈도가 낮은 사용자

## 3. 기존 파이프라인

기존 Talkiosk 파이프라인은 다음과 같이 구성한다.

```text
사용자 음성
    ↓
STT
    ↓
Menu Candidate Matching
    ↓
Rule-based NLU
    ↓
Schema Validator
    ↓
Order Engine
    ↓
TTS
    ↓
GUI
```

기존 구조에서 유지해야 할 핵심 원칙은 다음과 같다.

### 3.1 STT와 NLU의 역할 분리

STT는 사용자의 음성을 텍스트로 변환하고, NLU는 변환된 텍스트에서 주문 의도를 추출한다.

예:

```text
사용자:
"아이스 아메리카노 두 잔 주세요"

STT:
"아이스 아메리카노 두 잔 주세요"

NLU:
intent = ADD_ITEM
item = AMERICANO
temperature = ICE
quantity = 2
```

---

### 3.2 Order Engine이 주문 상태를 관리

가격, 수량, 옵션, 장바구니 상태 등의 실제 주문 정보는 NLU나 LLM이 직접 결정하지 않는다.

```text
NLU
 ↓
OrderCommand
 ↓
Schema Validator
 ↓
Order Engine
 ↓
Cart State
```

이를 통해 음성 인식이나 자연어 처리 오류가 발생하더라도 주문 상태를 제한된 규칙 내에서 관리할 수 있다.

---

## 4. 설문 반영 후 파이프라인

설문 결과를 반영한 파이프라인은 다음과 같이 확장한다.

```text
사용자 음성
    ↓
STT
    ↓
Menu Candidate Matching
    ↓
Rule-based NLU
    ↓
Intent 분기
    │
    ├─ 메뉴 탐색 / 검색
    ├─ 메뉴 정보 질문
    ├─ 주문 추가
    ├─ 수량 / 옵션 변경
    ├─ 취소 / 되돌리기
    ├─ 현재 주문 확인
    ├─ 다시 설명
    ├─ 천천히 설명
    └─ 주문 확정
    ↓
Menu DB / Order Engine
    ↓
Response Generator
    ↓
GUI + TTS
    ↓
사용자 확인 / 수정
```

핵심 변화는 **음성 입력 이후의 Intent 범위가 주문 생성뿐 아니라 탐색·질문·수정·복구까지 확장되는 것**이다.

---

## 5. Intent 확장

기존 주문 중심 Intent는 다음과 같이 구성할 수 있다.

```text
ADD_ITEM
REMOVE_ITEM
CHANGE_QUANTITY
CHANGE_OPTION
CONFIRM_ORDER
```

설문 결과를 반영하면 다음 Intent를 추가하는 것이 적절하다.

```text
SEARCH_MENU
ASK_MENU_INFO

UNDO
SHOW_ORDER

REPEAT
SPEAK_SLOWER
```

### 예시

#### 메뉴 탐색

```text
"안 단 음료 뭐 있어요?"

→ SEARCH_MENU
→ constraint:
   sweet = false
```

#### 메뉴 정보 질문

```text
"말차라떼가 뭐예요?"

→ ASK_MENU_INFO
→ item = MATCHA_LATTE
```

#### 수량 변경

```text
"아니, 하나만 주세요."

→ CHANGE_QUANTITY
→ quantity = 1
```

#### 직전 주문 취소

```text
"방금 거 취소해줘."

→ UNDO
```

#### 재설명

```text
"다시 말해줘."

→ REPEAT
```

#### 느린 안내

```text
"천천히 말해줘."

→ SPEAK_SLOWER
```

## 6. Menu Schema 확장

설문 결과에서 메뉴 탐색과 메뉴 질문에 대한 요구가 높게 나타났기 때문에, 기존 메뉴 스키마를 단순 주문 정보만 저장하는 구조에서 **의미 기반 탐색이 가능한 구조**로 확장할 필요가 있다.

### 기존 예시

```yaml
id: americano
name: 아메리카노
price: 4000

temperature:
  - hot
  - iced
```

### 확장 예시

```yaml
id: americano
name: 아메리카노
category: coffee

price: 4000

temperature:
  - hot
  - iced

attributes:
  sweet: false
  caffeine: true
  milk: false

description: 에스프레소에 물을 넣은 깔끔한 커피

keywords:
  - 안 단 음료
  - 커피
  - 깔끔한 음료
```

이를 이용하면 다음과 같은 질의를 별도의 복잡한 생성 모델 없이도 처리할 수 있다.

```text
"안 단 음료 뭐 있어요?"
→ attributes.sweet == false

"우유 안 들어가는 메뉴 있어요?"
→ attributes.milk == false
```

따라서 설문 결과를 반영했을 때 가장 많이 확장되는 부분 중 하나는 **Menu DB / Menu Schema**가 된다.

## 7. 주문 확인 과정 강화

설문에서는 음성 주문의 가장 큰 걱정으로 **내 말을 기계가 잘못 알아들을 가능성**이 나타났다.

따라서 음성 명령을 바로 최종 주문으로 적용하는 구조보다 다음 형태가 적절하다.

```text
사용자
"아메리카노 차갑게 두 잔 주세요."

        ↓

STT / NLU

ADD_ITEM
item = AMERICANO
temperature = ICE
quantity = 2

        ↓

Preview Cart

        ↓

GUI
아이스 아메리카노 × 2
8,000원

TTS
"아이스 아메리카노 두 잔을 담았습니다."

        ↓

사용자 확인 / 수정
```

사용자가

```text
"아니, 하나만."
```

이라고 말하면 Preview 상태에서 주문을 수정한다.

이 방식에서는 **STT 정확도를 높이는 것뿐 아니라, 잘못 인식되었을 때 사용자가 빠르게 발견하고 수정할 수 있는 구조**가 중요하다.

---

## 8. 주문 상태와 복구

설문에서 잘못 누른 뒤 처음부터 주문을 다시 시작한 경험이 다수 확인되었다.

따라서 Talkiosk에서는 사용자가 모든 주문을 처음부터 다시 시작하지 않고 직전 작업을 수정할 수 있어야 한다.

가능한 상태 관리 구조는 다음과 같다.

```text
Committed Cart
     ↓
Pending Command
     ↓
Preview Cart
```

### 예시

```text
현재 장바구니:
아메리카노 1잔

사용자:
"카페라떼도 하나 주세요."

→ Pending Command 생성
→ Preview Cart 표시

사용자:
"아니 취소해줘."

→ Pending Command 폐기
→ Committed Cart로 복귀
```

이 구조는 다음 발화를 자연스럽게 처리하는 데 도움이 된다.

```text
"방금 거 취소해줘."
"아니 그거 말고."
"하나만 주세요."
"아이스로 바꿔줘."
```

## 9. TTS 전략 변경

기존에는 고령 사용자에게 문장을 잘게 나누어 읽는 **분절형 TTS**를 주요 기능으로 고려할 수 있었다.

하지만 현재 설문에서는 일반적인 자연 발화가 분절 발화보다 더 높은 선호를 보였다.

따라서 기본 전략을 다음과 같이 단순화한다.

```text
Adaptive TTS
 ├─ 기본: 자연스러운 일반 발화
 ├─ REPEAT: 다시 설명
 └─ SPEAK_SLOWER: 느리게 설명
```

즉,

```text
고령 사용자
→ 항상 천천히 / 분절해서 말하기
```

보다는

```text
기본적으로 자연스럽게 말하기
        ↓
사용자가 필요할 경우
"다시 말해줘"
"천천히 말해줘"
        ↓
발화 방식 조절
```

이 더 적절하다.

## 10. GUI의 역할

설문 결과를 고려하면 Talkiosk를 **Voice-only 인터페이스**로 설계하는 것은 적절하지 않다.

음성 주문에서 오인식에 대한 불안이 존재하기 때문에, 사용자가 현재 시스템이 이해한 내용을 화면에서 바로 확인할 수 있어야 한다.

예:

```text
┌─────────────────────────┐
│ 아이스 아메리카노        │
│                         │
│ 수량: 2                 │
│                         │
│ 8,000원                 │
│                         │
│ [수정]        [확인]     │
└─────────────────────────┘
```

TTS:

```text
"아이스 아메리카노 두 잔,
총 8천 원입니다."
```

따라서 Talkiosk의 목표는 **GUI를 없애는 것**이 아니라,

> 복잡한 GUI 탐색은 음성으로 줄이고,  
> 중요한 주문 정보는 GUI로 명확하게 확인하게 하는 것

에 가깝다.

## 11. 컴포넌트별 변경 규모

| 컴포넌트 | 변경 정도 | 주요 변경 |
|---|---|---|
| STT | 낮음 | 기존 구조 유지 |
| Menu Candidate Matching | 낮음 | 기존 방식 활용 |
| Rule-based NLU | 중간 | 탐색·질문·복구 Intent 추가 |
| Schema Validator | 낮음 | 추가 Intent 스키마 대응 |
| Menu DB / Schema | 높음 | 속성, 설명, 검색용 메타데이터 추가 |
| Order Engine | 중간 | Undo, Preview, 수정 기능 강화 |
| TTS | 낮음 | 자연 발화 + 반복/속도 제어 |
| GUI | 중간 | 주문 확인·수정 UI 강화 |
| LLM | 낮음~중간 | 필요 시 메뉴 질문 fallback 용도 |
| State Management | 중간 | Pending / Preview 상태 관리 |

전체적으로 보면 다음 정도로 평가할 수 있다.

```text
아키텍처 자체 변경: 약 20~30%
기능 범위 확장: 약 40%
```

이는 정량적인 개발 공수 산정이라기보다, **기존 설계를 얼마나 유지할 수 있는지를 나타내기 위한 개략적인 표현**이다.

## 12. MVP 우선순위

현재 설문 결과를 기준으로 다음 순서로 구현 우선순위를 두는 것이 적절하다.

### Priority 1. 메뉴 탐색 및 질문

```text
"안 단 음료 뭐 있어요?"
"말차라떼가 뭐예요?"
"커피 아닌 거 추천해줘."
```

### Priority 2. 자연어 주문 및 옵션 수정

```text
"아메리카노 두 잔 주세요."
"하나는 아이스로 바꿔줘."
"하나만 주세요."
```

### Priority 3. 주문 확인

```text
"현재 주문 알려줘."
```

GUI와 TTS를 이용해 현재 주문 내용을 동시에 제공한다.

### Priority 4. 실수 복구

```text
"방금 거 취소해줘."
"아니 그거 말고."
```

### Priority 5. 재설명

```text
"다시 말해줘."
"천천히 말해줘."
```

## 13. 우선순위를 낮출 기능

현재 설문 결과만을 기준으로 다음 기능은 MVP 핵심 기능에서 우선순위를 낮출 수 있다.

### 분절형 TTS

일반적인 자연 발화에 대한 선호가 더 높아 기본 전략으로 사용할 근거가 부족하다.

### 결제 절차 자체 개선

현재 표본에서는 메뉴 탐색과 옵션 선택에 비해 결제 단계의 어려움이 상대적으로 낮았다.

### 음성만으로 모든 화면 대체

오인식에 대한 불안이 있기 때문에 화면 확인 기능을 유지하는 것이 적절하다.

### 단순한 글자 확대만을 핵심 해결책으로 사용

현재 결과에서는 글자 읽기보다 메뉴 탐색, 화면 구성, 옵션 선택 문제가 더 크게 나타났다.

## 14. 설문 반영 전후의 프로젝트 정의

### 기존

> 음성을 이용해 기존 키오스크 조작을 대신하는 시스템

### 설문 반영 후

> 복잡한 키오스크 화면을 직접 탐색하는 대신 자연어로 메뉴를 찾고 질문·수정하며,  
> 화면과 음성을 통해 주문 결과를 명확하게 확인할 수 있도록 하여  
> 고령 사용자가 스스로 주문을 완료할 수 있게 돕는 대화형 키오스크

## 15. 향후 설문 데이터 추가 시 확인할 항목

응답이 추가되면 다음 지표를 우선적으로 다시 확인한다.

1. 메뉴 탐색이 가장 큰 불편 요소로 계속 유지되는가
2. 옵션 선택의 어려움이 연령대가 높아질수록 증가하는가
3. 70대 이상에서도 음성 메뉴 질문에 대한 요구가 높은가
4. 디지털 숙련도가 낮은 집단에서 실수 후 재시작 비율이 증가하는가
5. 혼자 키오스크를 사용하는 사용자에게 음성 주문의 가치가 더 크게 나타나는가
6. 음성 오인식에 대한 우려가 실제 프로토타입 사용 후 감소하는가
7. 자연 발화 선호가 추가 표본에서도 유지되는가

현재 문서는 위 결과가 크게 달라질 경우 기능 우선순위를 다시 조정한다.
