# 말로(Mallo) Product Requirements Document

## 1. 문서 목적

본 문서는 말로(Mallo) MVP가 **어떤 사용자 문제를 해결해야 하며, 어떤 기능과 사용자 경험을 제공해야 하는지** 정의한다.

본 문서는 제품 범위와 P0/P1/P2 우선순위의 기준 문서다. 구체적인 시스템 구조와 모듈 경계는 TRD, 모델·데이터·수치·AC는 기능별 Spec에서 정의한다. 문서 책임과 충돌 처리 기준은 `docs/documentation-governance.md`를 따른다.

2026-08-28 기능동결 이후에는 새로운 상태 머신이나 옵션 기능을 추가하지 않고, 실제 구현·데모 흐름과 문서의 정합성을 우선한다. 일정 축소와 티켓 상태의 상세 근거는 `docs/final-ticket-reconciliation.md`를 따른다.

# 2. Product Overview

## 2.1 제품 한 줄 정의

**말로(Mallo)는 기존 시각·터치 중심 키오스크 이용에 부담을 느끼지만 일상적인 음성 대화가 가능한 고령 사용자가 사람에게 주문하듯 메뉴를 탐색·선택·수정·확인할 수 있도록 돕는 Voice-first 대화형 주문 시스템이다.**

사용자는 복잡한 메뉴 계층을 직접 탐색하는 대신 원하는 주문을 말하고, 시스템은 주문 내용을 음성과 큰 글씨로 확인해 준다.

안내를 이해하기 어렵다고 사용자가 명시적으로 표현하면 시스템은 발화 속도, Pause, 문장 분절 및 핵심 정보 전달 방식을 단계적으로 조절한다.

## 2.2 Product Vision

> **버튼을 없애는 것이 아니라 버튼을 찾아다닐 필요를 줄이고, 사용자가 듣기 어려워하면 말하는 방식도 바꾼다.**

사용자의 핵심 JTBD는 다음과 같다.

> **식당이나 카페에서 내가 원하는 메뉴를 실수 없이, 가능하면 다른 사람의 도움 없이 주문하고 싶다.**

음성 상호작용 측면에서는 다음 요구도 포함한다.

> **안내를 한 번에 이해하지 못했을 때 같은 말을 그대로 반복해서 듣는 것이 아니라, 내가 이해하기 쉬운 방식으로 다시 안내받고 싶다.**

# 3. Target User

## 3.1 Primary ICP

기존 시각·터치 중심 키오스크에서 다음과 같은 과정에 부담을 느끼지만 일상적인 음성 대화는 가능한 고령 사용자.

- 많은 메뉴와 시각 정보 탐색
- 작은 글씨 확인
- 여러 단계의 옵션 선택
- 반복적인 화면 조작
- 익숙하지 않은 UI와 용어 이해
- 잘못 선택했을 때의 수정
- 주문 내용 확인
- 뒤에서 기다리는 사람으로 인한 시간 압박

초기 사용자 조사는 65세 이상 사용자를 중심으로 수행하되 실제 조사 결과에 따라 세부 ICP를 조정한다.

## 3.2 현재 MVP의 Primary ICP에서 제외되는 사용자

- 음성 인터페이스 자체를 사용하기 어려운 사용자
- 지속적인 직원 보조가 반드시 필요한 사용자
- 완전한 Voice-only 인터페이스가 필요한 사용자

말로(Mallo)는 하나의 감각 채널에만 의존하지 않으며 **Voice-first + Minimal GUI**를 기본으로 한다.

## 3.3 사용자 조사 및 설문 근거

60대 고령 사용자 13명을 대상으로 수행한 키오스크 이용 및 음성 주문 설문 조사(`docs/survey-pipeline-update.md`)를 통해 다음 사용자 문제와 해결 방향을 실증적으로 확인했다.

1. **메뉴 탐색 및 옵션 선택 지연 (8/13명)**: 메뉴 찾기 및 복잡한 옵션 선택에서 가장 큰 어려움을 겪음 → 음성 기반 메뉴 탐색/질의(`SEARCH_MENU`, `ASK_MENU_INFO`) 및 Menu DB 속성 확장으로 해결
2. **실수 시 주문 재시작 부담 (7/13명)**: 조작 실수 후 전체 주문을 처음부터 다시 시작하는 번거로움 발생 → 직전 상태 복구(`UNDO`) 및 프리뷰 기반 장바구니 상태 관리 도입
3. **음성 오인식 불안 (6/13명)**: 음성만 사용하는 환경에 대한 불안감 존재 → 큰 글씨의 화면(GUI)과 음성(TTS)을 결합한 즉각적 주문 확인 피드백 제공
4. **자연스러운 발화 선호 (10/13명 재설명 의향)**: 분절형 발화보다는 자연스러운 대화형 발화를 기본으로 하고, 사용자의 명시적 요청(`REQUEST_REPEAT`, `REQUEST_SLOWER`)에 따라 발화 속도와 상세도를 적응 조절

# 4. Product Principles

## P1. Voice-first, not Voice-only

메뉴 조회, 주문 추가, 수정, 삭제, 확인 등의 핵심 흐름은 음성으로 수행할 수 있어야 한다.

다만 주문 확인 및 오류 복구 과정에서는 큰 글씨와 제한된 터치 인터페이스를 함께 제공한다.

## P2. 중요한 주문 상태는 항상 확인 가능해야 한다

음성 인식 또는 자연어 해석 오류가 곧바로 오주문으로 이어져서는 안 된다.

사용자는 주문에 반영될 주요 정보를 음성 또는 화면을 통해 확인할 수 있어야 한다.

## P3. 사용자의 상태를 임의로 추정하지 않는다

시스템은 다음과 같은 정보만으로 사용자의 이해 상태나 청력 수준을 임의로 추정하지 않는다.

- 연령
- 응답 속도
- 침묵
- 터치 속도
- 반복 행동

Adaptive TTS는 사용자의 명시적인 요청에 의해 동작한다.

예:

- "다시 말해줘."
- "천천히 말해줘."
- "기본 속도로 말해줘."
- `[다시 듣기]`
- `[천천히 듣기]`
- `[기본 속도]`

## P4. 불필요한 질문을 최소화한다

사용자가 한 번에 충분한 정보를 전달했다면 정보를 항목별로 다시 질문하지 않는다.

예:

> "아이스 아메리카노 두 잔 주세요."

메뉴와 수량이 모두 명확하다면 메뉴명과 수량을 각각 다시 묻지 않는다.

## P5. 실패하더라도 기존 주문 상태를 보호한다

음성 인식, 자연어 해석 또는 입력 오류가 발생해도 이미 검증된 장바구니 상태가 임의로 변경되어서는 안 된다.

## P6. 음성과 GUI 중 더 쉬운 복구 수단을 선택할 수 있어야 한다

음성만으로 해결하기 어려운 모호한 상황에서는 화면에 제한된 후보를 크게 제시한다.

사용자는 음성 또는 터치 중 편한 방법을 선택할 수 있다.

# 5. MVP Scope

## 5.1 대상 매장

MVP는 하나의 가상 카페를 대상으로 한다.

- 메뉴 약 10개
- 메뉴별 제한된 옵션
- 고정 가격
- 가상 결제 완료 화면 시뮬레이션

가상 결제는 **주문 확정 이후 결제 완료 화면과 총액을 보여주는 데모 흐름**을 뜻한다. 실제 PG 연동과 백엔드 Order Session의 별도 결제 상태 저장은 최종 MVP 범위에 포함하지 않는다.

## 5.2 우선순위 및 일정 축소 원칙

2주 MVP 일정에서 모든 기능을 동일한 필수 조건으로 취급하지 않는다.

- **P0 — 데모 성립 최소선:** 이 항목이 완료되면 사용자가 대기 화면에서 `주문하기`를 한 번 누르고 매장/포장을 선택한 뒤, STT → NLU → 주문 검증 → 주문 상태 변경 → TTS/GUI 확인 → 가상 결제 완료 화면까지 하나의 완결된 흐름을 시연할 수 있어야 한다.
- **P1 — 말로(Mallo) 차별화:** P0 안정화 이후 구현한다. 고령 사용자의 이해 및 오류 복구 경험을 개선하는 Clarification과 Adaptive TTS를 포함한다.
- **P2 — 있으면 좋은 고도화:** P0/P1 완료 이후 여유가 있을 때 구현한다. 멱등성·관측성 등 핵심 주문 경험을 막지 않는 기술 고도화를 배치한다.

일정이 지연되면 **P2 → P1 순서로 범위를 축소하며, P0 주문 경로의 완결성과 안정성을 최우선으로 보호한다.** 기능동결 이후에는 이미 안정화된 주문 흐름을 바꾸는 신규 상태 머신보다 문서·평가·제출물 정합성을 우선한다.

| Priority | 범위 |
|---|---|
| P0 | `주문하기` 1회 → 매장/포장 선택 → 응답이 필요한 턴의 자동 Listening → 한국어 STT → NLU/OrderCommand → Schema Validation → Menu DB/Order Engine → 기본 TTS/GUI의 단일 주문 경로, VAD 발화 종료 감지, 오류 시 Cart 보호, 수동 마이크 재입력 Fallback, 가상 결제 완료 화면, Local NLU Fine-tuning 및 Baseline 전후 비교 |
| P1 | CLARIFYING, 제한 후보 기반 Voice/GUI 복구, Adaptive TTS Level 0~2, TTS Fine-tuning·도메인 적응 및 모델 비교 |
| P2 | 멱등성 고도화, 상세 관측성, 필요성이 검증된 Echo 방지 고도화 |

## 5.3 지원 기능

주문 세션은 `IDLE → 주문하기 → 매장/포장 선택 → 음성 주문 → 확인·수정 → 결제 완료 화면` 순서로 진행한다. 매장/포장은 메뉴 주문보다 먼저 화면 버튼 또는 음성으로 선택하며, 주문 전체에 `DINE_IN` 또는 `TAKE_OUT`으로 유지한다.

MVP는 메뉴 주문, 수량, HOT/ICE, 복수 메뉴, 추가·삭제·수정, Context 유지를 지원한다. 세부 옵션은 실제 구현된 메뉴별 범위에 한정한다. **Size 음성 주문·변경은 최종 일정 축소로 MVP 지원 범위에서 제외한다.** Schema나 실험 문서에 Size 관련 필드가 남아 있더라도 최종 서비스 지원을 의미하지 않는다. 우유 종류 변경도 지원하지 않는다. 구체적인 메뉴·옵션 값과 적용 가능 조합은 [`docs/specs/menu-catalog.md`](specs/menu-catalog.md), [`docs/specs/beverage-option-adjustments.md`](specs/beverage-option-adjustments.md), 매장/포장 계약은 [`docs/specs/order-fulfillment-selection.md`](specs/order-fulfillment-selection.md)를 따른다.

### FR-01 메뉴 조회 [P0]

사용자는 음성으로 메뉴 종류를 질문할 수 있어야 한다.

예:

> "커피 종류가 뭐가 있어?"

시스템은 현재 판매 가능한 관련 메뉴를 안내한다.

### FR-02 주문 추가 [P0]

사용자는 메뉴와 수량을 자연어로 주문할 수 있어야 한다.

예:

> "아메리카노 두 잔 주세요."

### FR-03 주문 수정 [P0]

사용자는 기존 주문의 수량 또는 지원되는 옵션을 변경할 수 있어야 한다.

예:

> "아이스 아메리카노 세 잔으로 바꿔줘."
> "아이스 아메리카노를 따뜻하게 바꿔줘."

### FR-04 주문 삭제 [P0]

사용자는 장바구니의 특정 품목을 제거할 수 있어야 한다.

예:

> "아이스 아메리카노는 빼줘."

### FR-05 현재 주문 조회 [P0]

사용자는 언제든 현재 주문 내용을 질문할 수 있어야 한다.

예:

> "내가 지금 뭐 시켰지?"

### FR-06 주문 확인 및 확정 [P0]

시스템은 최종 확정 전 다음 핵심 정보를 사용자가 확인할 수 있도록 제공한다.

- 메뉴명
- 수량
- 주요 옵션
- 총액

사용자는 음성 또는 화면을 통해 주문을 확정하거나 수정할 수 있어야 한다.

최종 MVP에서는 **ORDER_REVIEW 화면을 주문 전체에 대한 명시적 확인 단계**로 사용한다. 개별 주문 추가·삭제·수정마다 별도의 Pending Confirmation 상태를 만들지 않고 변경 결과를 Cart와 시스템 안내에 즉시 반영하여 사용자가 확인·수정할 수 있게 한다. 별도 Pending Confirmation 저장·재확인·실행 상태 머신은 기능동결 범위에서 제외한다.

### FR-07 가상 결제 [P0]

주문 확정 이후 실제 PG를 연결하지 않고 결제 완료까지의 사용자 흐름을 시뮬레이션한다.

최종 MVP의 가상 결제는 **결제 완료 UI와 총액 표시까지**를 범위로 한다. 백엔드 Order Session에 `payment_status`를 추가하거나 승인번호·승인 실패·환불 등 결제 트랜잭션 생명주기를 모사하지 않는다.

## 5.4 NLU 주문 명령 계약

NLU는 사용자 발화와 현재 Context를 구조화된 `OrderCommand[]`로 변환하고, 결정론적 Order Engine만 검증된 주문 상태를 변경한다.

- 사용자의 한 발화에 포함된 주문 요청을 빠짐없이 구조화할 수 있어야 한다.
- 유효하지 않거나 모호한 요청은 기존 주문 상태를 변경하지 않아야 한다.
- NLU는 주문 상태를 직접 변경하지 않고, 명령 검증과 실행은 Order Engine이 담당한다.
- 주문 전체의 최종 확인은 ORDER_REVIEW UI/음성 흐름에서 수행하며, 별도 Pending Confirmation 상태 머신을 최종 MVP 요구사항으로 두지 않는다.

구체적인 wire format과 필드 규칙은 [`docs/specs/order-command.md`](specs/order-command.md), 실행·원자성·오류 규칙은 [`docs/specs/order-engine-operations.md`](specs/order-engine-operations.md)를 따른다. 기존 Spec에 더 넓은 확인 정책이 남아 있는 경우 최종 기능동결 범위는 본 PRD와 `docs/final-ticket-reconciliation.md`를 우선한다.

# 6. Voice Input Requirements

## FR-08 주문 세션 시작과 자동 Listening [P0]

말로(Mallo)는 대기 상태에서 항상 듣지 않는다. 사용자가 대기 화면의 `주문하기` 버튼을 한 번 눌러 주문 세션을 시작한 뒤 매장/포장을 터치 또는 음성으로 선택한다.

세션이 시작된 뒤 사용자 응답이 필요한 시스템 질문·안내가 끝나면 다음 흐름을 기본으로 한다.

> **TTS 종료 → 자동 Listening → 사용자 발화 → VAD 기반 종료 → 처리**

- 매 발화마다 Tap-to-talk를 요구하지 않는다.
- TTS 재생 중에는 마이크를 비활성화하고, 실제 재생 종료 후에만 Listening을 시작한다.
- 자동 Listening은 사용자의 직접적인 응답이 필요한 턴에서만 시작한다.
- 최종 주문 확정, 결제, 주문 완료 단계에서는 Listening을 종료한다.
- Listening 상태는 화면에서 명확히 확인할 수 있어야 한다.

## FR-09 수동 마이크 재입력 Fallback [P0]

수동 마이크 버튼은 다음 상황에서 동일한 입력 경로를 다시 시작하는 Fallback이다.

- STT 인식 실패 또는 사용자의 재입력 요청
- 자동 Listening이 Timeout으로 종료된 경우
- 사용자가 추가 주문을 다시 시작하는 경우

수동 마이크는 자동 Listening을 대체하는 매 턴 기본 조작이 아니다. Wake Word, 대기 상태의 Always Listening, TTS 중 발화를 받는 Barge-in은 MVP 범위에서 제외한다.

## FR-10 발화 종료 [P0]

사용자의 발화가 끝났다고 판단되면 시스템은 자동으로 음성 입력을 종료하고 처리를 시작한다.

발화 종료 자동 감지가 정상적으로 동작하지 않을 경우 사용자가 입력을 직접 종료할 수 있는 방법을 제공할 수 있다.

자동 Listening과 수동 마이크 Fallback 모두 동일한 VAD 발화 종료 정책을 사용한다.

## FR-11 음성 입력 실패 복구 [P0]

다음 상황에서는 주문 상태를 변경하지 않고 사용자에게 다시 입력할 기회를 제공한다.

- 자동 Listening 또는 수동 마이크 재입력 이후 응답하지 않은 경우
- 발화가 지나치게 짧은 경우
- 입력이 비정상적으로 빨리 종료된 경우
- 시스템이 발화를 정상적으로 처리하지 못한 경우

자동 Listening에서 일정 시간 동안 응답이 없는 것은 오류로 간주하지 않는다.

Listening만 종료하고 질문 상태와 기존 Cart를 유지하며, 사용자가 GUI 또는 수동 마이크로 응답할 수 있도록 한다.

# 7. Interaction Status Requirements

## FR-12 시스템 상태 표시 [P0]

사용자는 현재 시스템 상태를 쉽게 알 수 있어야 한다.

최소 다음 상태를 구분한다.

- 대기
- 듣는 중
- 처리 중
- 말하는 중
- 확인 필요
- 추가 확인 필요
- 오류 / 재시도

자동 Listening과 수동 마이크 재입력 모두 `듣는 중` 상태를 명확하게 표시한다.

예:

> 🎤 말씀해 주세요

사용자가 시스템이 현재 자신의 음성을 듣고 있는지 알 수 있어야 한다.

## FR-13 처리 시작 피드백 [P0]

사용자가 말을 끝낸 직후 시스템은 모델 처리 완료를 기다리지 않고 즉각적인 처리 시작 피드백을 제공한다.

기본 방식:

- 짧은 비언어적 효과음(Earcon)
- 큰 글씨의 처리 상태 표시

예:

> ● 주문을 확인하고 있어요

불필요한 음성 안내를 반복적으로 제공하지 않는다.

처리 시간이 비정상적으로 길어지는 경우에만 추가 음성 안내를 제공할 수 있다.

# 8. Voice + GUI Requirements

## FR-14 핵심 정보 동시 표시 [P0]

다음 정보는 음성 안내와 함께 화면에서도 명확하게 확인할 수 있어야 한다.

- 메뉴명
- 수량
- 옵션
- 총액
- 현재 주문 내역

## FR-15 모호한 요청의 하이브리드 복구 [P1]

사용자의 명령 대상이 하나로 결정되지 않는 경우 시스템은 임의로 주문을 변경하지 않는다.

예:

장바구니:

- 아이스 아메리카노
- 따뜻한 아메리카노

사용자:

> "아메리카노 하나 빼줘."

시스템:

> "아이스와 따뜻한 아메리카노 중 어떤 메뉴를 뺄까요?"

시스템 발화와 동시에 화면에는 다음과 같이 제한된 후보를 표시한다.

> **어떤 메뉴인가요?**

`[아이스 아메리카노]`

`[따뜻한 아메리카노]`

시스템 발화 종료 후 자동 Listening이 시작되며, 사용자는 별도의 Tap 없이 메뉴명을 말하거나 화면의 후보를 직접 선택할 수 있다. 자동 Listening이 종료된 뒤에는 수동 마이크로 재입력할 수 있다.

선택이 완료되면 시스템은 기존의 모호했던 명령을 이어서 처리한다.

## FR-16 후보 최소화 [P1]

Clarification 화면에서는 전체 메뉴를 다시 보여주지 않는다.

현재 모호성을 해결하는 데 필요한 최소 후보만 제시한다.

# 9. Adaptive TTS Requirements

## FR-17 Level 0 [P1]

새 주문 세션은 기본 안내 상태인 Level 0에서 시작한다.

- 기본 발화 속도
- 기본 Pause
- 일반적인 문장 구성

## FR-18 Level 1 [P1]

사용자가 느린 안내를 명시적으로 요청하면 Level 1으로 변경한다.

- 발화 속도 감소
- Pause 증가
- 문장 간 구분 강화

## FR-19 Level 2 [P1]

사용자가 추가적인 이해 지원을 요청하면 Level 2를 사용할 수 있다.

- 짧은 문장 분절
- 메뉴명과 수량 분리
- 금액 별도 전달
- 핵심 정보 중심 안내

예:

> 주문은 두 종류입니다.  
> 아메리카노.  
> 두 잔.  
> 카페라떼.  
> 한 잔.  
> 총 금액은 13,500원입니다.

## FR-20 Level 하향 [P1]

사용자가 기본 속도 또는 더 빠른 안내를 요청하면 Level을 낮출 수 있다.

## FR-21 Session-level Adaptation [P1]

변경된 TTS Level은 현재 주문 세션 동안 유지한다.

새 주문 세션이 시작되면 Level 0으로 초기화한다.

장기적인 개인별 음성 프로필은 저장하지 않는다.

# 10. Minimal GUI Requirements

P0 화면은 최소 다음 요소를 포함한다.

- 대기 화면의 `주문하기`
- 매장/포장 선택 버튼과 음성 선택 안내
- 현재 주문 내역
- 큰 글씨의 시스템 응답
- Listening/Processing/TTS 상태 표시
- 수동 재입력용 마이크 버튼
- 주문 확인
- 다시 말하기
- 직원 호출
- 현재 시스템 상태

P1 구현 시 다음 요소를 추가한다.

- 다시 듣기
- 천천히 듣기
- 기본 속도
- 모호성 해소용 후보 버튼

화면은 기존 키오스크처럼 여러 단계의 메뉴 계층을 직접 탐색하도록 요구하지 않는다.

AI Cashier 캐릭터는 보조 UX 요소이며 MVP의 필수 성공 조건이 아니다.

# 11. Error Recovery Requirements

## FR-22 음성 인식 실패 [P0]

사용자 발화를 정상적으로 처리하지 못한 경우 기존 주문 상태를 유지하고 다시 말하기를 요청한다.

## FR-23 존재하지 않는 메뉴 [P0]

현재 메뉴에 존재하지 않는 메뉴는 주문에 추가하지 않는다.

가능한 경우 실제 메뉴 후보를 제한적으로 안내한다.

## FR-24 모호한 참조 [P1]

대상이 여러 개 존재하면 임의로 하나를 선택하지 않는다.

P0에서는 `target_item_id`와 `temperature`로 대상을 식별한다. 온도가 생략되어 HOT·ICE 후보가 둘 이상이면 `AMBIGUOUS_TARGET`을 반환하고 전체 발화를 다시 입력하도록 안내한다.

P1에서만 음성 질문과 GUI 후보를 함께 사용하여 대상을 명확하게 한다.

필수 온도가 누락된 ADD_ITEM도 P0에서 재질문하지 않으며, HOT/ICE를 임의로 선택하지 않은 `temperature=null` 상태로 처리한다. 세부 Command 계약은 `docs/specs/nlu-add-item.md`를 따른다.

## FR-25 반복 실패 [P0]

반복적인 음성 입력 또는 재안내에도 주문 진행이 어려운 경우 `[직원 호출]`을 명확하게 제공한다.

현재까지의 장바구니 내용은 유지한다.

# 12. Happy Path

## 12.1 P0 Happy Path

1. 사용자가 대기 화면의 `주문하기`를 한 번 누른다.
2. 시스템이 매장/포장을 묻고 TTS 종료 후 자동 Listening을 시작한다.
3. 사용자가 화면 또는 음성으로 `DINE_IN`이나 `TAKE_OUT`을 선택한다.
4. 시스템이 메뉴 주문을 요청하고 TTS 종료 후 `듣는 중`을 표시한다.
5. 사용자가 "아이스 아메리카노 두 잔 주세요."라고 말한다.
6. VAD가 발화 종료를 감지하고 짧은 Earcon과 함께 `주문을 확인하고 있어요`가 표시된다.
7. 시스템이 주문을 해석·검증해 Cart에 반영하고 화면과 TTS로 안내한다.
8. 응답이 필요한 다음 턴이면 TTS 종료 후 자동 Listening이 다시 시작된다.
9. 사용자가 추가·수정·삭제를 이어가며, 확정된 Context는 유지된다.
10. 사용자가 "이제 계산할게."라고 말하면 시스템이 전체 주문·매장/포장·총액을 안내하고 최종 확정을 요청한다.
11. TTS 종료 후 사용자가 음성 또는 ORDER_REVIEW 화면으로 주문을 확정한다.
12. 시스템이 가상 결제 완료 화면과 최종 총액을 표시하고 Listening을 종료한다.
13. 사용자가 `새 주문 시작하기`를 선택하면 Cart, 주문 세션과 TTS Level을 초기화한다.

- Size 음성 주문·변경 지원
- 모든 음식점 대응
- 대규모 메뉴 탐색 UX

- RAG

- 완전한 Voice-only UI
- 복잡한 추천 시스템

# 14. Performance Requirements

정상적인 Warm 주문 Turn에서 사용자 발화 종료부터 말로(Mallo)의 첫 음성 응답 시작까지의 Time to First Audio는 **1.5초 이내를 요구사항**, **1.2초 이내를 목표**로 한다. Time to Visual Response와 Cold Start는 별도 지표로 측정한다.

Mock Pipeline이나 개별 TTS/STT Benchmark 수치는 실제 E2E 충족 근거로 사용하지 않는다. 구체적인 측정 경계, 판정, Provider Fallback 순서는 [`docs/specs/e2e-latency.md`](specs/e2e-latency.md)를 따른다.

## Experiment D — Multimodal Fallback [P0/P1]

- 자동 Listening 실패 후 수동 마이크 또는 GUI로 복구할 수 있는가

# 17. Future Considerations

## Large-menu Discoverability

MVP는 약 10개의 제한된 메뉴를 대상으로 한다.

향후 실제 매장 수준으로 메뉴가 확대되면 사용자가 메뉴명을 모르는 상태에서 음성만으로 탐색하기 어려울 수 있다.

이 경우 다음 방식을 별도로 검토한다.

- 카테고리 기반 음성 탐색
- 대표 메뉴 시각화
- 큰 이미지 기반 후보 선택
- 음성과 화면을 조합한 단계적 메뉴 탐색

해당 기능은 현재 MVP에는 포함하지 않는다.
